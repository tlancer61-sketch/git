# 协作与扩展

## 提交流程

1. 从 main 建 codex/<topic> 分支。按“规则 → 数据与来源 → 报告与内容”提交，PR 写明目的、文件范围、验证结果和待核实项。
2. 数据提交必须带来源记录；检查 JSON、引用、相同 ID、年款/配置适用性、证据独立性、价格有效期和隐私。
3. 内容评审检查推荐依据、竞品条件、利益关系、素材权利和平台格式。合并代码不等于授权发布；发布仍需用户明确指令。
4. 同一车型不建立重复真相表；修改字段说明后再新增字段。事实修正同时检查受影响的报告。
5. 不提交真实用户资料、销售聊天截图、密钥或未获授权的全文资料。匿名示例也要剔除可重新识别个人的组合信息。

## 命名与状态

- vehicle_id：品牌-车系-年款-能源-配置的英文稳定 ID。
- source_id：src-机构-日期-序号；没有日期用 undated，避免伪造日期。
- content_id：日期-选题短名；关联 vehicle_id、匿名 brief_id、数据 commit SHA。
- 内容状态：idea → researching → drafting → reviewing → ready → published；阻塞另记 blockers，撤稿为 withdrawn。
- ready 要求关键事实通过核实、冲突说明完成、图片可用、平台适配完成；published 必填链接、时间和人工复核人。

## 后续扩展顺序

先完整跑通一款真实车型、一个匿名需求、一个内容项目，再按需要增加：
1. JSON Schema、引用检查脚本和持续集成，阻止无来源或失效数据混入正式稿。
2. 积累稳定字段后导出 CSV/SQLite；JSON 仍保留可审阅历史，迁移决定另记。
3. 增加平台渲染器和素材索引，避免各平台稿件重复维护事实。
4. 客户数据保持私有，确有业务需要后再设计权限和 CRM 集成。
5. 抓取和发布适配器须单独设计授权、频率限制及失败恢复。

## 初始提交顺序

空仓库先提交 README.md 建立 main，再提交规则与忽略文件，接着数据与需求模板，最后 Skill、内容模板和流程。首次初始化可将后三组作为一个原子提交，避免模板之间的引用短暂缺失。
